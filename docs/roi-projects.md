# Witness projects: evidence before an ROI claim

20 September 2026. These public Java demonstrations are authored mechanism tests. They contain no generated tests, automatic migration, autonomous repair or measured customer benefit. Their receipts include actual executions, negative controls and inconclusive outcomes. Metrics are rendered from validated reports, never typed into marketing copy.

All caps are planning hypotheses subject to qualification and agreement, not delivery capacity or savings promises. One bounded trusted nonproduction component or fixture is the unit of work. Exclusions and acceptance conditions are project-specific in each brief. Terms and permitted data must be agreed before code or data is shared. The website prepares a manual conversation; it sends no contact message.

## Why investigate these problems?

Sources checked 20 September 2026:

- [DORA's 2025 report overview](https://dora.dev/research/2025/dora-report/) describes AI as amplifying existing organizational strengths and weaknesses. This supports investigating acceptance and review practices alongside tools; it does not establish the value of these projects.
- [Diffblue Cover's official documentation](https://cover-docs.diffblue.com/get-started/what-is-diffblue-cover) describes a commercial Java/Kotlin test-generation product with IDE, CLI and CI delivery. That is evidence of an existing product category, not independent proof of its vendor claims or demand for Test Witness.
- [Trunk's official flaky-test product page](https://trunk.io/flaky-tests) presents detection and quarantine as a commercial workflow. CI Witness's deterministic controlled cases do not establish flaky-test detection performance or statistical reliability.

Our inference is that test acceptance, behavior preservation and reproducible failures are reasonable discovery topics. These sources are category and problem indicators, not buyer interviews, conversion evidence, commitments or proof that a buyer will purchase an Odin pilot. Migration demand in particular remains a discovery hypothesis; no upgrade-market sizing is claimed.

## What would establish value?

Each scoped brief has a blank ROI worksheet. Agree a comparable baseline and accepted outcomes. Count setup, execution, human review and rework, task frequency, fully loaded labor rates, tool costs and the pilot fee. Separate one-time work from recurring effort. Disclose unresolved work and avoid extrapolating beyond the measured scope. Engineering capacity released is distinct from realized cash savings; actual cash savings need actual spending reductions. Runtime or fixture detection counts cannot be converted into human savings.

Track Odin's delivery labor, preparation, review, rework, support and tool costs separately. Contribution is agreed revenue less full delivery costs. No pilot has supplied these measurements here.

## Public integration

Each project uses the shared witness viewer, with generated static metadata, metrics, a selected observation and an all-observations table. Selection reads the embedded receipt using textContent; the browser never runs Java. The reproduction command requires Node 22 and JDK 21 and runs trusted bundled sources locally. Build/check integration validates receipts and source freshness. Source hashes establish consistency, not authenticity against wholesale rewriting. The page's current receipt determines its recorded time and source; a local record must never be described as a hosted CI run.
