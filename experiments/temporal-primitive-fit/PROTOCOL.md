# When would MongoDB earn an Odin platform primitive?

Authored 19 October 2026; draft until the source freeze. This is a separately frozen follow-on to the completed temporal-document-fit study. The earlier protocol, source and evidence remain unchanged. A successful compatibility test did not establish comparative advantage. This follow-on deliberately seeks the strongest fair MongoDB opportunity and can reject it.

## Grounding and boundary

Inspection of implemented local Odin call chains found bounded session state, heterogeneous execution artifacts, session event cursors, and nested work-order state. PostgreSQL JSONB already implements governed memory with transactional version checks, history and idempotency. These are code-grounded workload shapes, not measurements of live traffic or deployed behavior. No private source, customer data or runtime payload is exported. Fixtures and frequencies below are synthetic assumptions.

Candidate documents contain stable identifiers, extensible nested tool state and a bounded cold body. Both database models support flexible fields. The question is whether native document operations provide a material benefit after PostgreSQL is allowed a suitable physical design. A single-document result does not establish the multi-record history/receipt contract of governed memory or work orders.

## Frozen matrix

The machine-readable protocol.json is authoritative for counts, limits and thresholds. A measures direct adapter requests on 1,000 documents over ten tenants, with 8 and 64 KiB cold bodies (serialized documents also include identifiers, versions and nested state). Each profile has five repetitions, 100 warm-up requests and 1,000 counted requests at concurrency ten per design. Profiles are known-hot state (80% updates/20% full reads), distributed scalar updates (90%/10%), and a read-heavier distributed profile (50%/50%). Distributed updates rotate across 64 existing numeric leaves in 32 tool-state objects. No adapter receives a different request trace. Ten active documents (one per lane) are revisited among the 1,000-document background. Before counted distributed profiles, each active document receives 64 uncounted mutations covering all 64 paths, followed by the standard warm-up. This establishes mature overlays rather than first writes. The hot set and uniform path distribution are stress assumptions, not production-frequency claims.

MongoDB uses native path updates with an optimistic version guard. PostgreSQL uses both native JSONB path updates and a split model: a dedicated hot-state row for the known-hot profile, and immutable base JSONB plus a generic leaf-override table for distributed profiles. The version guard and override change commit atomically. Split-model full reads reconstruct the same document, using one retrieval rather than a query per leaf; reconstruction belongs inside measured latency. All designs return the same small mutation acknowledgment and the same complete document on reads. A duplicate expected version is a conflict, not a general durable idempotency receipt. Overlay compaction is not measured and remains an operating obligation.

B measures 10,000 documents over ten tenants, each with 20 of 200 scalar attributes. Known and withheld keys are fixed before counting; indexes cannot be added after query inspection. Twenty fixed queries balance numeric equality, string equality, numeric range, explicit empty value and existence across both groups, with positive values chosen deterministically from the seeded fixtures. Empty-match, wrong-type and absent-key cases are separate correctness controls. MongoDB uses a tenant-aware compound wildcard index. PostgreSQL uses both JSONB GIN with explicit predicates and typed attribute rows with a tenant/key/type/value index. The normalized alternative need not redundantly maintain the JSON document. Each of five repetitions includes 100 uncounted warm-ups, 500 measured queries, and 100 separately measured attribute updates. Queries return sorted bounded identifier/value projections. Complete expected matching sets and present/absent/explicit-no-value/type distinctions are verified outside timing. Attribute maintenance, ingestion, index build and storage are reported alongside query latency.

A totals 90,000 counted requests, and B totals 9,000: 99,000 main requests if every cell completes. The separate full-matrix reproduction uses one repetition and a second declared seed (19,800 requests); it is never pooled with the main timings. These counts are protocol commitments, not results.

## Fair timing and correctness

One direct adapter invocation is timed through response decoding and any required reconstruction. Expected values, fixture generation, whole-document verification, evidence hashes and Temporal scheduling are outside the timed interval. Fixed per-lane traces avoid arm-dependent scheduling changing selected records. Arm order rotates in a fixed Latin square. Each cell begins with its declared fixtures/indexes; warm-up and measured traces are distinguishable. All requests, failures, conflicts, per-operation latency and result hashes are retained, including partial failed cells. Full snapshots are independently compared in memory; stored session evidence retains actual mutable/core fields and each cold body’s length/SHA256, plus the full-snapshot digest. Frozen source/seed reproduce the synthetic cold bytes. Whole-cell throughput is harness throughput, including trace bookkeeping; request latency has the narrower boundary above.

Independent expected-state and query oracles establish correctness; agreement between databases is insufficient. Controls include stale/duplicate version rejection, competing updates, mismatched existing tenant/id keys, missing records, wrong-path/type semantics, deliberately corrupted reconstructed state and deliberately corrupted query results. Any unsupported or incomplete control prevents a candidate verdict. Driver-level operation timeouts, observed owned-process RSS, elapsed time and disk limits fail closed and preserve partial evidence. No heavy owned website/build/test jobs overlap counted work.

A separate real Temporal activity check exercises the same adapter contract and commit-before-ack retry with read-backed reconciliation on isolated known state. It is not included in kernel timings and does not claim arbitrary exactly-once processing, deployment-version replay, production failover, or MongoDB as Temporal persistence.

## What would justify MongoDB?

For each declared workload/size, MongoDB must pass every correctness control and beat **both** PostgreSQL alternatives. The preregistered screening bar is at least 30% lower median request latency in at least four of five paired repetitions, with median paired p95 ratio no worse than 1.10 and maximum paired data-plus-index storage ratio no greater than 2.0 against each PostgreSQL alternative. Attribute query candidates additionally cannot hide more than a twofold update-latency regression against the best PostgreSQL design. The fixed mixed-query workload and each declared known/withheld query class are evaluated separately, with every outcome reported; a pooled median cannot establish a range-query advantage. All individual comparisons, storage, build/ingestion and maintenance costs remain visible; no favorable composite score is invented.

The independent reproduction must preserve the declared advantage and correctness/latency/storage gates. A win only over monolithic JSONB is labeled JSONB-only, not PostgreSQL superiority. A win in one profile does not transfer to other profiles. No threshold, request count, fixture or comparator is changed after counted results are observed. Implementation mistakes require a retained invalid run, a documented forward amendment, new source freeze and complete rerun.

Passing establishes a **local candidate advantage for a bounded primitive**, not a production-wide migration. A production adoption decision still needs actual workload share and a saving large enough to cover a second database's monitoring, backups, on-call, migration and consistency obligations. Tenant-key scoping is tested; independently authenticated identities and database-enforced isolation are not established here. No developer-hours claim is inferred from lines of code or one agent's implementation time.

## Scope decisions this experiment can support

A justified outcome could be a Mongo-backed bounded session/artifact store, with PostgreSQL retaining relational authority and governed history. A second could be a Mongo metadata-search projection while PostgreSQL remains the source of truth; its freshness/rebuild obligations must be tested before adoption. A negative result supports retaining PostgreSQL. None of these outcomes justifies putting all platform data in MongoDB. Event-stream retention, logical decoding/change-stream recovery, HA/PITR, sharding and operating-cost break-even need distinct future contracts rather than setup-step counts.

## Sources and reproducibility

Pinned native versions and exact dependency locks are recorded in protocol.json. Record source, lock, fixture and binary hashes before measurement. All raw rows and failures are retained, and only reviewed synthetic evidence is exported. Official technical grounding: PostgreSQL 16 JSON types/indexing and data-modifying WITH, MongoDB 8.0 wildcard indexes and atomic writes (URLs in protocol.json). PostgreSQL WAL bytes and MongoDB oplog bytes are different diagnostics and cannot be labeled an apples-to-apples write-amplification ratio.


## Amendment: macOS flush methods (19 October 2026)

The first counted run was interrupted after 81 complete cells when read-only diagnosis found PostgreSQL using its `open_datasync` default. PostgreSQL documents `fsync_writethrough` as the macOS setting that prevents disk write caching. MongoDB 8.0.15's pinned WiredTiger source attempts `F_FULLFSYNC` on supported macOS builds; we have not traced the actual syscall branch. Nominal synchronous/journal acknowledgments alone did not establish equivalent physical flush mechanisms. The initial timing comparison is confounded, not evidence of intrinsic database efficiency.

The amended run requires observed PostgreSQL `wal_sync_method=fsync_writethrough`, with `fsync`, `synchronous_commit`, and `full_page_writes` enabled, before any counted adapter mutation. MongoDB retains majority-plus-journal acknowledgments. Both the entire main matrix and distinct-seed reproduction restart under this setting; thresholds, workloads, seeds and operation denominators are unchanged. No earlier observations are pooled. The interrupted run, operator reason, diagnosis, and its exact frozen sources remain available as excluded evidence.

This narrows the platform configuration mismatch; it is not a syscall trace, proof of identical hardware flush behavior, or a sudden-power-loss test. Results remain local macOS screening. Other operating systems require an explicitly reviewed equivalent durability configuration.

Reference: https://www.postgresql.org/docs/16/wal-reliability.html

Live settings are checked before adapter mutations and again at run end. A setting drift, pending restart, nonempty `PGOPTIONS`, or the pinned WiredTiger full-flush fallback warning rejects the run. Absence of that warning is not a syscall trace.
