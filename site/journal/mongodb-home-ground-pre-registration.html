EXP 020: MongoDB on its home ground: where does it fit Odin?

EXPERIMENT NOTE / 009 · EXP 020 · PRE-REGISTERED 25 OCT 2026 · AMENDED 25 OCT 2026 · S2 RUNNING

Our two earlier MongoDB studies, EXP 013 and EXP 014, were careful, but they tested what PostgreSQL already does well. This study tests what MongoDB is built for. It takes four problems Odin has on record and asks, for each one, which database solves it correctly, with fewer operational components, at equal or better cost, when each gets its best realistic design.

There is no overall winner. Each of the four problems gets its own verdict: MongoDB fits, PostgreSQL fits, both fit, or neither. Before the plan was frozen, one reviewer argued for MongoDB's best design and one for PostgreSQL's, and either could veto a setup that would handicap its side. Both reviews are published below, in full.

Status: pre-registered; S2 is running, and amendment 01 publishes changes made to it after it started (below). This plan was written, hashed and merged to main before any counted run. Counted runs start only after the commit that publishes it. Nothing in it may change afterwards, except by a dated amendment that is published first.

The four problems

They come from Odin's own decision records, listed in EXP 010's design study (section 1). Each one maps onto a native MongoDB mechanism, and none has been measured.

  • S1: one serializer rule for both arms (keys in stored order).
  • S2 faults: the consumer is killed at seeded points, the database restarts once per cell, and the consumer is down for a frozen 10 minutes. Either side may persist its token or cursor together with the effect in one transaction. The oplog and the slot get the same disk budget (oplogMinRetentionHours / size against max_slot_wal_keep_size), and lost history is classified the same way in both arms. maxAwaitTimeMS, batch size and the poll interval are frozen and recorded.
  • S3 "append-only": the application role cannot update or delete. It holds INSERT, SELECT only (PostgreSQL) or a custom role with find + insert (MongoDB), and an application update must fail (permission denied / code 13). A read filter (expireAt > now / row-level security) is allowed on both arms; the no-extension variant always runs. Two cells: (a) default cadences, 60 s on both, grace 150 s at 1× and 240 s at 10×; (b) tuned cadences, 5 s (ttlMonitorSleepSecs = 5, a 5 s sweep), grace 30 s at 1× and 60 s at 10×. Physical and visible expiry lag p50 / p95 and write p95 during expiry are reported.
  • S4: the baseline is Odin's current pattern, fetching the values and aggregating in the application. Matching index allowances on both arms. Application peak memory, bytes over the wire and 1× are reported.

How a verdict is decided

  • mongodb-fits / postgres-fits: the store passes the gate, and either beats the other store's best variant on the primary latency metric by at least 20% on the median, in at least 4 of 5 paired repetitions, with the same direction in the reproduction; or, for S3, and as a tie-break for S2, has at least 2 fewer components.
  • both-fit: both pass, and neither condition holds.
  • neither: neither passes. invalid: a cell is incomplete, or source or durability drifted.
  • Repetitions: 5 paired repetitions per cell, with the arm order alternating, plus a separate-seed reproduction of every cell.
  • Publication: every cell, every variant, every outcome.

Counting moving parts

A frozen checklist, and both counts are published. One component each for: every process or container beyond the database server; every extension not in core; every server setting changed off its default and needed for correctness; every persistent non-data object (a slot, publication, trigger, policy, partition scheme counted once per scheme, TTL index, custom role or keyFile); every scheduled job; and every safety alarm an operator must watch (an oplog window, slot retention). MongoDB pays for its replica set, keyFile, oplog sizing and oplog alarm. PostgreSQL pays for its slot, publication, wal_level, jobs and partitions.

An even setup

  • MongoDB Community 8.0.x as a one-member replica set (replSet, rs.initiate), auth on with a keyFile, writes w: majority, j: true, PyMongo 4.x.
  • PostgreSQL 16.x, the official image plus pinned derived images where an extension is used (wal2json, pg_cron, pg_partman), synchronous_commit = on, psycopg 3.x. Each scenario also runs a no-extension variant.
  • Equal resources: 4 GB / 2 CPU per database container. MongoDB: WiredTiger cache 1.5 GB. PostgreSQL: shared_buffers 1 GB, effective_cache_size 2 GB, work_mem 64 MB, max_parallel_workers_per_gather 2, --shm-size 1 GB. Default compression on both (snappy, pglz), recorded; driver wire compression off.
  • Host: Windows + WSL2 Docker Desktop, data on named volumes on the WSL2 ext4 disk, never on NTFS bind mounts. pg_test_fsync and fio --fsync=1 run inside each container and are recorded, with mongod's filesystem warning. The client runs in a container on the same Docker network, with equal pool sizes. A macOS machine runs the same frozen source as a second-OS replication.
  • Before each cell: PostgreSQL runs VACUUM ANALYZE and CHECKPOINT; the cache is warm on both arms, after one discarded pass; checkpoint and autovacuum events are logged. Image tags and digests are pinned before the first counted run and recorded in the run manifest.

The two reviews

Each reviewer was an independent model reviewer (Claude, fresh context), briefed to make sure its database got its best realistic design. Every veto was accepted. The PostgreSQL review caught a factual error in the draft ("json loses indexing" is false), an outbox that would drop late commits, and an append-only rule that favoured MongoDB. The MongoDB review pinned the decode type and payload placement for S1, tied the S3 grace to the configured TTL interval, and equalised retention for S2. Both asked for a primary metric, a margin and a definition of a component.

What this does not establish

Named as the next study, not judged here: failover with a 3-member replica set against Patroni (S5), sharding, multi-region, and search / vector search. Failover is MongoDB's home ground, so it is named explicitly; on one shared Docker host a fair PostgreSQL arm for it (streaming replication with Patroni and etcd) is a memory and stability risk to both arms. The run does not imply anything about any of them. EXP 013 and EXP 014 stand as published; this experiment does not change or replace them.

Amendment 01: changes to S2's runner, published late

This plan says a change is a dated amendment, published first. For S2, the change-feed scenario, that did not happen. Its runner was changed four times, and given a rule for which counted cells count, after this plan was published and after S2's first two counted cells ran. Those two cells ran on the old code and were discarded; every kept cell ran under the changes. Amendment 01 (also on this site) publishes all of it before S2's report, and we own the gap.

  • 01: the pgoutput cursor became the commit LSN, fixing a runner bug that lost one event.
  • 02: every arm applies changes in batches of up to 100 per transaction. Effect and cursor still share one transaction, but this moves the measured lag a long way, so it is published as a change to the measure.
  • 03: the producer builds its payloads before its clock starts, a harness timing fix that restores the planned rate.
  • 04: the MongoDB consumer applies once its local buffer is empty. It is for one arm only and in that arm's favour, so it is published as a change to the measure.
  • Which cells count: a counted cell that overlapped heavy work on the host (a browser run, filming, another benchmark) is discarded and re-run. Nine cells were discarded under that rule; five of them had first been kept. All nine are listed by id in the amendment.

The S2 runner's protocol is published too. The amendment also records that the protocol pairs MongoDB with the better PostgreSQL variant per repetition, while this plan says "the other store's best variant"; it does not settle that, and any change is a further amendment before the report. S1, S3 and S4 are not affected.
