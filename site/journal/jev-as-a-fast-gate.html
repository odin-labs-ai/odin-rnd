Jev as a fast gate: the pre-registration

EXPERIMENT NOTE / 002 · EXP 005 · PRE-REGISTERED 26 SEP 2026 · NO RESULTS YET

Pre-registered, no results yet. This note is published before any gate has seen a single item of the corpus. It is the plan, fixed in advance: what we ask, what we measure, and what would prove us wrong. Written, hashed and published before any gate (Jev, Laya or the LLM reviewer) sees a corpus item. Nothing in this record may change after publication; a later change is a new, dated pre-registration, and the results are judged against this one.

The question

Given only a unified diff and a plain-language statement of the architecture rules, can a System-1 typed-decision model (Jev, hosted) serve as a fast first gate that tells whether an agent-written change breaks a rule, so that a cascade which escalates its unsure calls to an LLM reviewer misses no more drift than the reviewer alone, at a fraction of the reviewer's cost?

The ground truth is the blueprint engine, bce-engine 0.3.1, run on the real tree after each change. bce is deterministic and cheap wherever a blueprint and the tree are wired in.

This experiment asks a different question: whether a typed-decision model can triage a change from the diff alone, before merge, where bce is not wired in, with escalation to a heavier reviewer. It does not test replacing bce, and no result here would support using a typed-decision model instead of it.

Laya, an open-weight typed-decision model, answers the same inputs and is reported against the same criteria. The claim under test is Jev's.

Why a diff-only triage is not a replacement for bce

bce needs a blueprint and the real tree; given both, it answers exactly and costs little. A check that sees only the diff and the rules as text, before merge, is a different setting. There the typed gate would sit in front, settle what it is sure of and pass the rest on. bce stays what every gate in this experiment is scored against.

The cascade

For each item: when Jev decided with confidence at least 0.9, Jev's decision is final, whether ACCEPT or REJECT. Otherwise (lower confidence, or a Jev abstention) the item is escalated and the cascade takes the reviewer's decision; a reviewer abstention on an escalated item is a cascade abstention.

The escalation rate, the cascade's missed drift and false reject, and its cost per 1,000 decisions (Jev on every item plus the reviewer's k runs on escalated items only).

How each gate decides

  • For Jev and Laya, the decision is REJECT (the gate predicts RED) when p is at least 0.5, and ACCEPT (the gate predicts GREEN) otherwise.
  • For Jev and Laya, confidence = max(p, 1 - p). A confidence the service reports alongside p is recorded but not used.
  • A reviewer run's decision is read from the result text: the first line anywhere in it that matches ^VERDICT: (APPROVED|REJECTED) (multiline, case-sensitive). APPROVED is ACCEPT and REJECTED is REJECT. A run with no matching line is an abstention.
  • The reviewer's decision for an item is the decision that more than half of its k runs gave (2 of 3). Anything else, including a tie and too many abstaining runs, is an abstention.
  • An abstention is reported separately for each gate and is never recoded into a decision. In the headline figures and the criteria it counts against the gate.
  • A failed call (network or HTTP error, timeout, unexpected served model, malformed answer, refused input, a client error) is an abstention. Failures are kept in the record with their reason.

The corpus

A small layered TypeScript service (domain, app, infra, config) with a blueprint of import-boundary and environment-variable rules, and 60 authored changes to it (c001 to c060). Half of the changes were written to break a rule in one of five families (reverse layer import, infrastructure leak, forbidden configuration key, re-export from a governed file, dynamic import); half were written not to, and 16 of those are near-misses (an allowed import next to a forbidden one, a test-only change, a comment that mentions a rule). The ids are shuffled, so their order does not follow the families. bce's label, not the author's intent, is the truth.

bce (bce-engine 0.3.1, extractor ast) labels 30 of the 60 changes RED and 30 GREEN; 0 labels disagree with their author's intent and 0 items are excluded. Each change is applied to a fresh copy of the base tree, committed as the only commit of a fresh git repository and scored. Exit 0 with verdict pass, score 100 and no violations is GREEN (the change breaks no rule). Exit 1 with verdict fail, a score below 100 and at least one violation is RED (the change breaks a rule). Any other combination is an error, never a label.

Corpus sha256 fcf7d61b214ced984c1073abc3b8a0ba6551b489efc9e01d2104c142390a7e47: sha256 of experiments/jev-gate/corpus.sha256, which lists the sha256 of every file the labels depend on: base/, corpus/, blueprint.json, rules.txt, gate-question.json, corpus-spec.json, manifest.json and labels.json.

Gate inputs sha256 b18397b6918542b2413425bb82fa2e0b44ad794f0dad852302e0a552e48d4dac: sha256 of experiments/jev-gate/inputs.json, the one input every gate receives for each item. It carries no labels. Jev and Laya get the same state, built as state = rules.txt + "\n\n" + diff, and this question:

{"type":"noul","instructions":"Does this change break any of these rules?"}

The rules, verbatim:

Architecture rules for this TypeScript service. They govern every .ts file under src/. An import is any import in the file itself: import, import type, export ... from, and import().
Files in src/domain must not import anything from src/app.
Files in src/domain must not import anything from src/infra.
Files in src/domain must not import anything from src/config.
Files in src/domain and src/app must not import the pg package.
Files in src/app may use infrastructure only through src/infra/index.ts; they must not import any file in a folder inside src/infra.
Only src/config may use process.env; files in src/domain, src/app and src/infra must not contain process.env anywhere.
Files in src/config may use only these environment variables, written as process.env.NAME: PORT, DATABASE_URL, LOG_LEVEL, SMTP_HOST, SMTP_FROM, INVOICE_PREFIX. Any other process.env name, or process.env[...], is not allowed.

The gates

  • Jev, the gate under test: model jev-1.13.0 through jev-ai.pro, an independently operated reseller of TypeSafe's hosted System-One API (not TypeSafe itself), at https://jev-ai.pro/api/v1/systemone. One call per item, sequential, in id order, never retried.
  • Laya, the open-weight comparison: huggingface.co/convaiinnovations/laya at revision 55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851. The EXP 004 MLX port (experiments/laya-vs-jev/laya_mlx.py) on the Apple GPU, one call at a time. laya_inputs.build_sequence(tokenizer, state, gateQuestion, max_len 1024, head_max_len 256) with the same state as Jev. No input may be cut: laya_count.py measures every part before the cut and refuses any input that does not fit, and the built inputs record 0 truncated items.
  • The LLM reviewer: nina (github.com/xhulz/nina) — used with the permission of its author, as confirmed by Odin Labs. Release 0.28.10 (commit efcc5229fc2c5d5f39b740280efd4307b8a8537b), agent reviewer, run by Claude Code 2.1.280 with model claude-opus-5-5 at effort high, 3 runs per change. Tools: Read, Grep, Glob, Bash(git diff:*), Bash(git status:*), Bash(git show:*), Bash(git log:*). A fresh temporary git repository per run, composed with the nina CLI at the pinned release (nina init, nina compose). One base commit with the neutral message "base" holds the base tree (without node_modules), rules.txt at the repository root, the .claude/ directory and CLAUDE.md that nina compose writes, and a .gitignore that excludes run artefacts. The change is applied with git apply and left uncommitted, so git status and git diff show exactly the change. bce, the blueprint, the labels and every other experiment file are absent. No web access; no tool outside the list above.

The reviewer's prompt, verbatim. Written for this experiment by Odin Labs. It contains no text from nina's reviewer specification.

Review the change in this repository. The change is everything that git diff shows; it has not been committed. The architecture rules this codebase must follow are in rules.txt at the repository root. Decide one thing only: does the change break any of those rules? Ignore style, naming, tests and anything else that rules.txt does not state. Do not edit any file. Explain your reasoning briefly, then write your decision on a line of its own: VERDICT: REJECTED if the change breaks at least one rule, or VERDICT: APPROVED if it breaks none.

Baselines Jev has to beat

Each baseline is a deterministic, committed script that decides every corpus item from inputs.json alone, with no model and no network. Its result on the pinned corpus is computed and recorded here before any gate call. The results report each baseline as a row that Jev has to beat, on the same items and metrics; a typed gate that does not do better than a script adds nothing the script could not.

The baseline rows are being recorded and are not part of this version of the record.

experiments/jev-gate/baselines.json: each entry's id, script path, the script's sha256 and its results. The validator reads that file and every script from disk and refuses any difference.

The better baseline is the one with the fewest missed RED items on the pinned corpus (primary population), computed from baselines.json before any gate call; a tie goes to fewer false rejects, then to the id that sorts first. Its id is recorded here; it is null only while no baseline is recorded.

What we measure

  • agreement: Items whose decision equals bce's label, over all items in the population. An abstention counts as not agreeing.
  • missedDrift: Headline, worst case: RED items the gate ACCEPTED or abstained on, over all RED items in the population (false accept; the primary metric for a gate). An abstention on a RED item counts as missed drift.
  • falseReject: Headline, worst case: GREEN items the gate REJECTED or abstained on, over all GREEN items in the population. An abstention on a GREEN item counts as a false reject.
  • abstentionRate: Items with no decision, over all items in the population, reported separately for RED and GREEN items. Abstentions already count against the gate in the headline figures.
  • decidedOnly: Missed drift and false reject with abstentions excluded: RED items ACCEPTED over RED items the gate decided, and GREEN items REJECTED over GREEN items the gate decided. Reported beside the headline figures, not used for the criteria.
  • accuracyAtHighConfidence: For Jev and Laya: among decided items with confidence at least 0.9 (the cascade's threshold), the fraction whose decision equals bce's label, with the count of such items.
  • cascade: The cascade's missed drift, false reject, abstentions and escalation rate, as defined in cascade.rule.
  • reviewerVariance: Items whose k reviewer runs did not all give the same decision (an abstaining run counts as a different outcome), over all items; and each run index's missed drift and false reject on its own.
  • latency: Wall time of each call measured by our own wrapper, p50 and p90 per gate. Jev's includes the public internet.
  • costPer1000: Cost per 1,000 decisions per gate and for the cascade, each labelled with its basis (see cost).

Every rate is published with its Wilson score interval at 95% (z = 1.959963984540054): (p + z^2/(2n) ± z * sqrt(p(1 - p)/n + z^2/(4n^2))) / (1 + z^2/n), with p the observed proportion of n items.

The cascade is compared with the reviewer on the same items with the Newcombe hybrid score interval for the difference of paired proportions (method 10, without continuity correction): On the same n RED items, for the first (the cascade, or Jev) against what it is compared with (the reviewer, or the better baseline), with an abstention counted as a miss: a = both miss, b = only the first misses, c = only the other misses, d = neither. p1 = (a + b)/n (the first), p2 = (a + c)/n (the other), theta = p1 - p2. (l1, u1) and (l2, u2) are the Wilson intervals of p1 and p2. phi = (ad - bc)/sqrt((a + b)(c + d)(a + c)(b + d)), and phi = 0 when that denominator is 0. delta = sqrt((p1 - l1)^2 - 2 phi (p1 - l1)(u2 - p2) + (u2 - p2)^2); epsilon = sqrt((u1 - p1)^2 - 2 phi (u1 - p1)(p2 - l2) + (p2 - l2)^2). The interval is (theta - delta, theta + epsilon).

Every corpus item whose bce label agrees with its author's intent and that bce did not exclude. The criteria are judged on this population. Every corpus item that bce labelled, including items whose label disagrees with the author's intent. Reported beside the primary figures; not used for the criteria.

What would prove it wrong

  • Jev misses more than 10% of drift (RED items it accepts or abstains on).
  • Jev falsely rejects more than 25% of clean changes (GREEN items it rejects or abstains on).
  • The cascade misses more drift than the reviewer alone, on the same RED items (an abstention counts as a miss for both).
  • Jev misses more drift than the better model-free baseline, on the same RED items (an abstention by Jev counts as a miss).

The claim is refuted if any criterion is refuted. Every criterion uses the headline (worst-case) figures. Laya is judged against the same two single-rate criteria and reported; its result does not decide the claim.

Each criterion comes out in one of three states: refuted, passes, not established at this N, passes. Compare the point estimate with the threshold. Refuted: the point estimate is greater than the threshold. Passes, not established at this N: the point estimate is not greater, but the upper bound of its Wilson interval is. Passes: the upper bound is not greater than the threshold either. Compare the point estimates of the headline missed drift on the same RED items. Refuted: the first (the cascade, or Jev) misses more than what it is compared with (theta greater than 0). Passes, not established at this N: it does not miss more, but the Newcombe interval of theta includes 0, as it does for a tie. Passes: it does not miss more and the interval lies entirely below 0. All three states are published as they come out, with the counts and intervals behind them.

If the reviewer itself misses more than 20% of drift (headline point estimate), the cascade comparison is reported as uninformative: it is neither refuted nor passed.

A sanity check only. Latency is reported and is not a criterion. Our wrapper measures wall time; it is one busy machine, and Jev's latency includes the network.

Cost, the spending cap and timing

  • Jev: $0.242 per million input tokens. Listed price: the highest listed annual-plan rate on jev-ai.pro/pricing (read 2026-09-24, as in EXP 004; output tokens listed as free), multiplied by the input_tokens the response reports. Not an invoice. A response without usage has no cost figure, and the gap is reported.
  • Reviewer: API-equivalent: the total_cost_usd that the Claude Code client reports for each run, at list price. Not an invoice; the runs may be billed differently.
  • Laya: Runs locally with no per-call price. Hardware and electricity are not measured.
  • Costs on different bases are shown side by side, each with its label; they are never presented as the same kind of figure.
  • A cap of $100, of which $0.30 is already spent. Paid gate spend only: Jev at its listed price and the reviewer at its API-equivalent cost, including the one reviewer check already run while planning ($0.30). Agent time is outside the cap. A running ledger adds the cost of every paid call to $0.30. Before any paid call, if the ledger plus the largest single-call cost seen so far for that gate (for the reviewer, at least $0.30) would exceed the cap, the run stops. A stopped run is published as partial, with the ledger.
  • The publication readiness gate is retried at most 10 times per publish, each attempt logged with its time and outcome. After the last failed attempt, the publish stops and the failure is reported. Timeouts and gate settings are never changed to make a retry pass. Gate calls (Jev, Laya, reviewer runs) are never retried. A failed call is an abstention (decisionRules.failures).
  • Every gate call records its local start and end time in UTC. Every Jev call also records the HTTP Date header of the server's response next to the local clock. The time this pre-registration was merged on odin-rnd main, recorded after publication. Every gate call's local start time, and every Jev Date header, must be later. A call that is not is excluded and reported.

What this does not establish

  • 60 items (30 RED, 30 GREEN) give wide 95% intervals. A criterion can pass on its point estimate and still not be established at this N; the record says which.
  • Headline figures count every abstention against the gate: a miss on a RED item, a false reject on a GREEN one. A gate that fails or declines often looks worse for it; the figures with abstentions excluded are published beside them.
  • The reviewer and the typed gates do not see the same thing. The reviewer works in a repository with read and git tools; Jev and Laya see only the diff and the rules as text. The comparison is between the two setups as they would be used, not between the models alone.
  • Jev is reached through jev-ai.pro, an independently operated reseller endpoint, not directly from TypeSafe. The served model is checked on every answer.
  • Costs are at listed or API-equivalent prices, not invoices, and the two bases differ.
  • One author wrote the corpus and the rules. An independent review checked the corpus before these hashes were fixed.
  • bce reads direct import edges. A breach that only happens through a file outside the governed scope is invisible to it, so that family is not in the corpus.
  • One machine and one run. Latency describes that machine under its load at the time.
  • Confidence here is max(p, 1 - p) for both typed gates. EXP 004 used the confidence Jev reported and, for Laya's yes/no answers, one minus the normalised entropy, so the two experiments' confidence figures are not comparable.
