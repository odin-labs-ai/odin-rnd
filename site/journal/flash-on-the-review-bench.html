A free model on our review bench

RESEARCH NOTE / 005 · 21 OCT 2026 · LOCAL EXPERIMENT

The first study showed that MiniMax M3.1 Flash can point at the broken line in code it has never seen. This follow-on asks the question a reviewer actually faces: given a whole change, does it say "fix this" when there is a defect and "ship it" when there is not?

On our sealed review corpus, Flash caught as many real defects as Claude Opus and raised about as many false alarms. It caught 16 of 30 defects in both of its standard-prompt runs (Opus caught 16 and 19 in an earlier calibration) and flagged 21 and 19 of 30 clean changes (Opus flagged 20 and 18). At list price that is about 1.5 cents a review. No reviewer we have measured, Flash included, flags few enough clean changes to be given a vote.

The corpus and the bar

The corpus was assembled before this trial and sealed: 30 real defects from our own review history, 30 clean changes that were merged and never fixed afterwards, 58 diffs in all. A reviewer sees one diff and a neutral description, nothing else. The existing scorer, unchanged, counts a catch only when the verdict is not "ship" and a finding names the defective file. A clean change that does not get "ship" is a false alarm.

The bar we set for a reviewer that may vote: at most 2 of 30 clean changes flagged in a run, so that the 95% upper bound stays at or below 25%. In the earlier calibration, no seat met it; the strictest run flagged 6.

What we ran

Flash and gpt-oss:120b, our current default for offloaded work, each ran twice per prompt (replicates a and b). Prompt P1 is the live review contract. P3 adds an enumerated fault model: a blocking finding must name one of seven fault classes and a concrete failing input. Both models ran as a tool-free reviewer: one direct call to the model API, with no tools and no file access. Why that matters is the second half of this note.

A no-verdict (a timeout, or an HTTP 429 or 500 while the account was saturated) counts as a miss on a defect and as a false alarm on a clean change, so these figures are conservative. Three of the four planned Flash runs were complete when this note was written. The fourth, P3 · b, was restarted after an accounting abort and is still running.

Flash against our default, case by case. In each paired run, Flash caught more defects that gpt-oss:120b missed than the reverse: 8 against 3 (P1 a), 7 against 3 (P1 b) and 11 against 3 (P3 a). The direction is consistent, but no single run is significant at this size (exact paired p = 0.23, 0.34 and 0.057). Replicates replay the same cases, so they are not pooled. On clean changes the two are level on P1. On P3, gpt-oss:120b got more clean changes right because it ships more of everything.

Flash repeats itself. Between its two P1 runs, only 2 of the 30 defect outcomes flipped. In the earlier calibration, seats flipped between 4 and 9. A reviewer that gives the same answer twice is one you can calibrate.

Unlike the seats in the earlier calibration, Flash did not shed false alarms under P3: 20 against 21 and 19. It kept its recall (15 of 30), though.

The finding that matters more than the score

We first ran Flash through our general agent runtime, the way earlier reviewer seats were run, from an empty scratch directory. It did not stay there. With a shell tool available, it left the directory, found the developer checkout on the machine and searched it with git log and grep. That checkout contains the sealed answer key and the real fix history. Every command it ran was read-only, but nothing stopped it.

  • An empty working directory is a convention, not a sandbox. Any reviewer with tools can, in principle, look up the answer. Our earlier calibration seats also ran with tools; their numbers may be flattered, and we have not re-measured them yet.
  • “No tools” was not tool-free. With tools switched off, the runtime still exposed agent-spawning and dispatch tools. Flash used them: 15 context loads, a spawned agent and 3 dispatches. It never finished within the 900-second limit. The same prompt as one direct API call answered in 69 seconds.
  • A silent model swap. During a brief failure to reach the model catalogue, the runtime quietly answered with a different model from another provider under Flash's name, and that call was billed. Our scorer checks the model named in each receipt, so that answer would have been discarded, but the money was already spent.
  • Tools may flatter a reviewer. gpt-oss:120b caught 17 and 14 defects through the agent runtime but 11 and 12 as a tool-free reviewer. Some of that gap could be answer-key access. This data cannot separate the two.

We now measure reviewers through a tool-free seat. It makes one HTTPS request to a fixed endpoint and has no tools, no filesystem and no configuration lookup. Its model identity is checked against the response, and its cost is computed exactly from the receipt.

Why it matters

Measured: a free open-weight model matches a frontier model on catching real defects in our own changes, at a small fraction of the cost, and is unusually consistent between runs. Measured: no reviewer we have tested yet raises few enough false alarms to vote on its own. Expected, not measured: that a cheap, high-recall reviewer paired with a strict one could beat either alone.

Evidence and its boundary

This is an internally evidenced experiment. The diffs come from private repositories, so cases, findings and answers are not published; the counts are. The corpus, scorer and prompts were fixed before this trial; this study's own run plan was locally frozen, not publicly pre-registered. Runs took place on 21 October 2026, starting 11:51 UTC, on one laptop. Every run ended with the canonical review log byte-for-byte unchanged. The Claude Opus rows come from an earlier calibration on the same corpus (14 October 2026) and were measured through a seat with tools.

What remains open

  • Re-measure the earlier seats through the tool-free path before any voting rule is written.
  • Whether a reviewer can talk itself out of its false alarms. That is the next pre-registered experiment.
  • Latency outside peak hours. Up to eight runs shared one account at peak times, so Flash's five-to-seven-minute medians are an upper bound.
  • The fourth Flash run (P3 · b).
