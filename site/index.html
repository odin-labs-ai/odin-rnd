How a piece of work
earns its place.

The idea behind every station, followed through one change. Scroll to watch it move from a written rule to a published record.

  1. 01 / BLUEPRINT
    domain → app: forbidden

    Write the rule down.

    Before the work starts, we write down what must stay true. Here: the core business code (the domain) may not reach into the app built on top of it.

  2. 02 / WORKCELL
    CHANGE ACHANGE B

    Let the work happen.

    An agent or a person makes a change. We also keep a copy we broke on purpose, to test the check itself.

  3. 03 / GATE
    A · GREENB · RED

    Check it against the rule.

    The same unchanged rule runs on both. A useful check lets the correct change through and stops the broken one.

  4. 04 / RECORD
    RECORDED

    Publish what happened.

    The result goes on the record with its date, its exact inputs and its limits, whether it supports us or not.

Experiments,
with their results.

Each one asks a question whose answer could go against us, and shows its input, its result and its limits. What the model-provider experiments show so far is under provider economics; what we have measured, and not keeps measured and unmeasured apart.

Would your tests notice?

The test passed. The bug survived. We planted a tiny rounding mistake: a weak test suite missed it, a careful one caught it, and a fake that always says “pass” was turned away.

Test Witness · small Java examples we wrote

What if both versions are wrong?

Old and new code agree, and both are wrong. Comparing them to each other would approve the move, so we check both against what the answer should be, written down separately.

Migration Witness · small Java examples we wrote

Did the fix break something else?

The failing test is green again, but something else broke. We try both shortcuts on purpose: a fix that breaks other code, and a fix that deletes the check. The acceptance step must reject both.

CI Witness · small Java examples we wrote

Can a written rule catch a change that breaks it?

We write down one rule about how the code is built, for example “this part may not depend on that part.” Then we run it on two copies of a project: one that follows the rule, and one we broke on purpose. In all three recorded runs the check passed the first copy and flagged the second. See the runs and the command to repeat them

Then a decision you can own.

We asked an open model on a laptop and a hosted model the same questions, each one a pick-an-option, a score or a yes or no. The open model gave the same answers as its reference code and, network included, answered faster. But it fell further behind the hosted model on accuracy than the limit we set before the run, so that check failed. See the full comparison

What these results
don’t show.

These experiments make failure easy to see, on small examples we wrote. They do not show savings for a customer, that someone else got the same result, or how an agent will do on work it has not seen.

23.10.26RESEARCH NOTE / 010

EXP 019: Routing by our own rulebook, measured again

Three fresh, complete runs of the routed arm on the same eight tasks, scored by the share of hidden test cases fixed. Routing paid 14.3 cents per case fixed (57% of cases), against EXP 018's 24.7 for always-Opus (65%) and 4.3 for always-Luna (52%). Pre-registered verdict: routing beats always-Opus, within a wide replicate allowance, and does not beat always-Luna.

↗
23.10.26RESEARCH NOTE / 009

EXP 018: Does routing by our own rulebook beat one fixed model on real tasks?

Eight real coding tasks, three arms, three runs each, scored by the share of hidden test cases fixed (no task was fully solved). Per case fixed, a table copied from our routing rule paid 13.3 cents (61% of cases), always Opus 5.5 paid 24.7 (65%) and always GPT-6 Luna paid 4.3 (52%). The pre-registered verdict is incomplete: one routed cell hit its spend stop.

↗
23.10.26RESEARCH NOTE / 008

EXP 016: Does the same model cost the same through every broker?

Almost. Measured on 720 identical calls: two brokers billed exactly list price for Claude Sonnet 5.5 and GPT-4o mini, the third 10% above it on both, a spread of 1.10 against a pre-registered bar of 1.05. No broker served a different model.

↗
23.10.26RESEARCH NOTE / 007

EXP 017: What does a defect caught in review cost, model by model?

Four models on one tool-free review seat caught between 26 and 31 of 60 defects, all within noise, at 0.06 to 8.3 cents a review. gpt-oss-120b, MiniMax M3.1 Flash and Claude Opus 5.5 are on the pre-registered frontier; Claude Sonnet 5.5 is not.

↗
22.10.26RESEARCH NOTE / 006

EXP 012: Can a reviewer talk itself out of its false alarms?

No. Asked to name a concrete failing input for every finding or drop it, MiniMax M3.1 Flash kept 249 of 269 of its own findings. False alarms stayed at 20 and 22 of 30 clean changes, against a pre-registered bar of 2.

↗
21.10.26RESEARCH NOTE / 005

A free model on our review bench

On a sealed corpus of 30 real defects and 30 clean changes, MiniMax M3.1 Flash's counts sat in Claude Opus's range at about 1.5 cents a review. No reviewer flags few enough clean changes to vote, and an agent-run reviewer can read its own answer key.

↗
21.10.26RESEARCH NOTE / 004

Can a free model find real bugs in our private code?

On bugs in our private fix history that can be found from the code alone, MiniMax M3.1 Flash's first guess landed within two lines of the fix 63% of the time, against 23% for our current default. Only about 1 in 10 of the small fixes we sampled could be found that way.

↗
19.10.26RESEARCH NOTE / 003

Where would MongoDB earn a place in Odin?

99,000 requests and a separate 19,800-request repeat found two advantages over monolithic JSONB, but none over the stronger PostgreSQL alternatives, for these workloads on one machine. All seventeen outcomes and the durability amendment are retained.

↗
19.10.26RESEARCH NOTE / 002

Does flexible workflow data need MongoDB?

Both stores passed 20,000 operations, 42 correctness checks and ten evolution suites behind Temporal activities. For this workload, a MongoDB advantage remains unresolved and flexible JSON alone gave no demonstrated reason to switch.

10.10.26EXPERIMENT NOTE / 008

EXP 011: Where does a model reviewer earn its keep?
the pre-registration

Every model-reviewer measurement so far used rules a hand-written checker already decides. EXP 011 asks the opposite: on the 18 rules EXP 007's census found no bce 0.3.1 constraint can decide, and which a code change can still break, does nina 0.34.0's reviewer tell violating changes from clean ones better than the frozen rule-filtered off-the-shelf tools, with both held to a false-reject rate of at most 15%? Pre-registered; not yet run.

09.10.26EXPERIMENT NOTE / 007

EXP 009: Unload leaves no trace:
the results

P1 refuted: 1 of 400 H1 trials diverged from R0 (95% Wilson upper bound 1.40%). P2 supported: 0 silent-inert and 0 false-inactive kernel configurations of 120. All 5 validity gates passed, so the record is informative.

02.10.26EXPERIMENT NOTE / 005

EXP 008: Hand over the cache, not the text:
the pre-registration

Two small open-weight models from different families, with different tokenizers. The sender reads a change and the rules once; the receiver must make the EXP 005 gate decision from the sender's KV cache, mapped into its own, without a forward pass over that context. EXP 008 measures whether that matches text re-prefill closely enough, and fast enough, to be worth having, on public baselines only. Pre-registered; not yet run.
