How we run
experiments.

You should be able to check any number on this site without asking us. This page says how: what we write down before a run, how it is frozen, what each experiment may spend, what would prove us wrong, who checks a change before it is published, and how to rerun it yourself. Every claim below points to a file in the repository.

Every experiment and its statusRerun it yourself

1. The question comes first.

Before any counted run, an experiment's pre-registration is written down and published. It states the question, what is measured, how it is scored, the decision rule, what the experiment may spend and its known limits. Each one lives in its own folder, for example experiments/self-verify/preregistration.json (EXP 012) or experiments/jev-gate/preregistration.json (EXP 005).

Where the analysis is code, the code is frozen with the question: EXP 008 pins its analysis script experiments/latent-handoff/analyse.mjs by hash in a dated amendment (experiments/latent-handoff/amendment-02.json), and EXP 005 recomputes its published results from the committed runs with experiments/jev-gate/results.mjs.

Two studies on this site were published without a pre-registration: EXP 013 and EXP 014, the MongoDB studies. They are numbered so they can be cited, and the experiment list marks them “not pre-registered”: their method and data are published, but nothing about them was fixed before they ran.

2. Frozen by sha256.

Each pre-registration has a .sha256 beside it, such as experiments/self-verify/preregistration.sha256, written when the record is pushed. The push time is the freeze time. After that the record does not change.

A change after the freeze is a new, dated file that names its parent by hash: an amendment (experiments/jev-gate/amendment-01.json, experiments/self-verify/amendment-01/amendment.json) or an erratum (experiments/jev-gate/erratum-01.json). The site build refuses to publish a record whose bytes no longer match its hash: see scripts/jev-gate-prereg.mjs and scripts/ledger-publish.mjs. The published copy under data/ is the record, byte for byte.

3. A spend bound on every run.

Every pre-registration bounds its spend (a spend block; EXP 005, the first, calls it spendCap): the most the run may cost and what happens when that bound is reached. In EXP 012, for example, the run stops and the experiment is published as incomplete, with the finished count; nothing is extrapolated.

Experiments that pay for model calls keep a per-call spend ledger next to their results, for example experiments/jev-gate/spend-ledger.jsonl, experiments/nina-changes/spend-ledger.jsonl and experiments/blueprint-floor/spend-ledger.jsonl.

4. Rules that can prove us wrong.

The decision rule is part of the frozen record, so the result cannot choose its own bar. Results are published whatever they show, and a refuted claim stays refuted. So far that includes EXP 005 (the claim is refuted), EXP 007 (the premise is refuted), EXP 009 (its first prediction is refuted) and EXP 012 (the answer is no). Each status sentence on the experiment list comes from the experiment's own note, unedited (scripts/experiment-ledger.mjs).

Before a pre-registration is written we sometimes run a few calibration calls. When we do, the record says so, and states what we expect, so the result can contradict it.

5. Checked before it is published.

Changes to this site arrive as pull requests. On each one, the verify job in .github/workflows/publish.yml reruns the three recorded experiments with the released engine, runs every test, builds the site and checks it (links, anchors, transcript digests and the public export boundary, scripts/check.mjs). The same job runs again on every push to main, before the site is deployed.

An independent review examines the final change on its exact head before it is merged (AGENTS.md). The reviewer is never the author of the change.

One gap is disclosed here. On 22 October 2026 a pull request was merged while its verify job was still running; that job then failed on a fence test whose base had moved, while the push run on main passed. Since 23 October our landing tool refuses to merge a pull request in this repository until verify has passed on its exact head. A rule on GitHub's side that requires the same check is waiting on the repository owner; until it exists, the landing tool is what enforces it.

6. Rerun it yourself.

With Node 22 and pnpm 10.11.1:

git clone https://github.com/odin-labs-ai/odin-rnd
cd odin-rnd
pnpm install --frozen-lockfile
pnpm experiment   # rerun the three recorded blueprint experiments
pnpm test         # every check on the recorded evidence
pnpm build        # build the site from the records
pnpm check        # links, digests, export boundary

The commands are in package.json and AGENTS.md; docs/VALIDATION.md records how the site itself was validated. For a single experiment, its folder holds the inputs and the frozen analysis; its field note says which parts you can rerun and which depend on a private corpus.

7. What this does not prove.

Most experiments here are small: one laptop, one model or a few dozen cases. Several use a private corpus, so you can check the hashes, the method and the counts but not rerun the cases. We wrote the experiments ourselves, about our own tools. A pre-registration stops us from moving the bar after the fact; it does not make a narrow question broad. Each field note states its own limits; read them before quoting a number.
