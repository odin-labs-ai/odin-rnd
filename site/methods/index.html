How we test, in plain words.

What we test.

We test AI models, coding tools and resellers of model access on work close to ours. They review code changes, fix bugs, answer quick yes-or-no questions and keep a database running through a failure. Most examples are ones we wrote ourselves or changes from our own code, not customer code.

Planned in writing before it runs.

Before the runs that count, we write down the plan. It says what we ask, what we measure, how we score it and what would count as a yes. It also says what the study may spend and what it cannot show. We publish the plan and lock it, so it cannot change quietly. A later change is a new, dated file that says what changed and why.

What a limit means.

Every result says what it does not show: how many examples, whose examples, which machine and which models. That is its limit. A limit is part of the result, not small print, so read it before you quote a number. When our own team runs a study again on another machine, that shows it repeats. It is not a check by an outside team.

When a result does not hold up.

If a result misses the pass mark written down before the run, we say the idea did not hold up. We do not soften that to “mixed”, and the result stays published. A negative result still tells you something: what not to rely on. In one study, a plain rule-checking script missed no rule breaks. A fast AI decision model missed one, so the AI was no better there. In another, an AI reviewer that double-checked its own findings still raised far more false alarms than the bar we set.

Why some results are exploratory.

A few studies were not planned in writing before they ran. They are exploratory: we publish their method and data, but nothing about them was fixed in advance. They are labelled separately in the experiment list and on their own pages, so you can tell them apart from planned studies. Treat them as leads, not settled answers.

The details +

A public number should have an inspectable method, date and source boundary. Some underlying corpora and operational receipts are private, so some results lack enough public material for outside reproduction. This page says how: what we write down before a run, how it is frozen, what each experiment may spend, what would prove us wrong, who checks a change before it is published, and how to rerun it yourself. Every claim below points to a file in the repository.

The two examples above are EXP 005 (its claim is refuted: a model-free line linter written from the same seven architecture rules missed none of the drift items, and Jev missed one) and EXP 012 (the answer is no). The exploratory studies are EXP 013 and EXP 014; the experiment list marks them “not pre-registered”.

Arm

One of the options a study compares, each run under the same conditions. We also say “option” or “setup”.

Example: EXP 018 compared three arms on the same coding tasks: routing each task by our own rulebook, and two fixed choices that always used the same model.

Blind run

A run in which the AI reviewer never actually read the change it was asked to review, so its verdict says nothing about that change.

Example: in EXP 005, the reviewer’s own tool fence kept it from reading the change in 131 of 180 runs. EXP 006 measured it again with a fence that allows the commands it uses.

Broker

A reseller of access to AI models: you pay the broker, and it passes your request on to the model. We name brokers by letter.

Example: in EXP 016 we sent the same requests through three brokers. Broker A and Broker C billed the list price; Broker B billed above it on both models.

Census

A survey that sorts every item in a set, here a set of rules.

Example: EXP 007 is a census of the rules that eight code-review plugins ship: for each rule, how much could a plain checker decide on its own, before any model is asked?

Counted run

A run that counts toward the result. A few trial calls made before the plan is written do not count, and the record says when there were any.

Example: EXP 009’s counted run was 40 blocks, starting on 8 October 2026.

Exploratory study

A study that was not planned in writing before it ran. Its method and data are published, but nothing about it was fixed in advance, so read it as a lead rather than a settled answer.

Example: EXP 013 and EXP 014, two database studies, are marked “not pre-registered” in the experiment list.

Factory, floor and station

Our words for the concept drawing on the home page, in which each station (a step: Blueprint, Workcell, Gate, Record, Decision, Triage, Floor) opens one separate experiment and its record. The stations are not stages that results pass through, and the drawing is not a map of real machines.

Example: the Gate station opens “A passing test missed the defect.”

Fixture

Test examples we wrote ourselves, not customer code. A result on them shows that a mechanism works on those examples; it does not show it works on unseen work or customer systems.

Example: the 60 code changes in EXP 005 were written by us and scored by our rules engine.

Frozen analysis

Analysis code fixed before the results came in, so it cannot be adjusted to fit them.

Example: EXP 008 pins its analysis script by its hash in a dated amendment, and EXP 005 recomputes its published results from the committed runs (see step 1).

Gate and validity gate

A gate is a check that a change or a result must pass. A validity gate is a check on the run itself: if the run fails it, the result does not count.

Example: EXP 005 asked whether a fast model could serve as the first gate on code changes. EXP 009 passed all five of its validity gates, so its result counts.

GREEN, RED, UNVERIFIED

Outcome labels, always written out in words as well as colour: GREEN means passed, RED means failed and UNVERIFIED means not checked.

Example: in EXP 004, a criterion stays UNVERIFIED when Jev was not run, and turns RED past its stated margin.

Harness

The test setup around a model: what it is given, which tools it may use, and how its answers are collected and scored.

Example: EXP 009 asked whether loading and unloading parts of our research harness leaves it the same as a fresh start. Its first prediction did not hold up: 1 of 400 trials differed.

Jev

A fast decision model from an outside vendor, which we call as a hosted service; it is not ours. It answers a typed question: pick one of these options, give a score, or say yes or no.

Example: EXP 004 compared Jev with Laya on 48 hand-written rows, on one laptop.

KV cache

A model’s working memory of text it has already read, kept so it does not have to read that text again.

Example: EXP 008 asks whether one model can make a decision from another model’s KV cache instead of rereading the text.

Latent handoff

Passing that working memory (the KV cache) from one model to another, instead of passing the text.

Example: EXP 008, planned in writing with no results published yet, is to measure on public examples only whether this matches rereading the text closely enough, and fast enough, to be worth having.

Laya

An open-weight decision model published by an outside team; it is not ours. It runs on a laptop, with no vendor key.

Example: EXP 004 asked whether Laya can answer the same typed decisions locally, so that a hosted model becomes a comparison rather than a dependency.

Limit

What a result does not show: how many examples, whose examples, which machine, which models and who ran it. Every finding states its limit; read it before you quote a number.

Example: the code-review finding on the home page is limited to our own changes and planted defects, reviewed without tools.

Linter

An ordinary rule-checking tool: a script that checks code against fixed rules, with no AI model.

Example: in EXP 005, a linter written from the same seven architecture rules missed none of the 30 rule breaks, and Jev missed one. Those were rules a plain check can decide.

Machine names

Names such as org-ci-heavy or ubuntu-latest are the computers that ran a check. Two of our machines agreeing shows the result repeats inside our organisation; it is not independent replication.

Example: the lab runs page lists each re-check with the machine that ran it.

nina

An AI code reviewer by an outside author, published on GitHub; it is not ours. We measure it.

Example: EXP 006 measured nina’s reviewer again on the same 60 changes as EXP 005, counting a run only when it showed the reviewer had read the change.

Pre-registered

We wrote down the question and what would count as a yes before running anything, published it and locked it by its hash. A later change is a new, dated file.

Example: EXP 012’s plan, experiments/self-verify/preregistration.json, set the bar for false alarms that its result then missed.

Record

The published file that holds an experiment’s results, with its dates and how it was run. Numbers on our pages are read from it when the site is built, and link to it.

Example: the code-review finding on the home page reads its prices and counts from the EXP 017 record.

Record hash (sha256)

A fingerprint of a file’s exact bytes: change one byte and the fingerprint changes. It shows that a file is the one we published; it does not show that the experiment was right or that a claim is true.

Example: each plan has a fingerprint file beside it, such as experiments/self-verify/preregistration.sha256.

Refuted, or a negative result

The idea did not hold up: the result missed the pass mark written down before the run. It is never softened to “mixed”, and it stays published.

Example: in EXP 012, a reviewer asked to check its own findings still raised false alarms on 20 and 22 of 30 clean changes, against a bar of 2. Step 4 lists the others.

SAME, with 0 breaches

What a re-check prints when a lab’s published result still matches its data: the counts taken again from the evidence give the same hash as the published record, and no group of counts differs. It counts again; it does not score or judge again.

Example: the re-checks on the lab runs page.

Seat

The setup a model works in, mainly whether it has tools. A tool-free seat sees only what we give it; an agentic seat can use tools and read files.

Example: EXP 017 put four models through one tool-free seat. Our earlier review measurements had used different seats, and one of them could read the answer key.

Silent-inert

A setting that looks switched on but silently does nothing.

Example: EXP 009 found no silent-inert settings among 120 configurations of its harness core, against 44 for the unchanged baseline filter.

Source card

A note beside an answer saying where it came from. It records attribution, not whether the answer is correct.

Example: answers in Lab 01, the agent space, carry source cards.

Strict-ack and acknowledgement gap

The acknowledgement gap is the longest wait, after a database switches to its backup copy, for the database to confirm to a writer that its data is saved. Strict-ack is a stricter setting in which a write is confirmed only once a second copy holds it.

Example: in EXP 021, the strict variants have an unresolved anomaly in the check that watches durability, and some files may overlap heavy work on the same machine. Both limits travel with the result.

System-1 decision model

A model that answers a typed question about a situation quickly: pick one of these options, give a score, or say yes or no.

Example: Jev and Laya, compared in EXP 004.

Uncertainty range

The range the true value could plausibly lie in, given how few examples we ran (an interval). When two results’ ranges overlap, neither is clearly ahead.

Example: in EXP 017, four reviewers caught between 26 and 31 of 60 defects, all inside one another’s intervals.

Value frontier

Best value for money: a model is on the frontier when no other model catches at least as many defects for no more per review.

Example: in EXP 017, under the rule written down beforehand, three of the four models were on the frontier and one was not.

What a public claim must establish.

In short: a public claim says only what its evidence supports, with its limits beside it. This standard applies to every page on this site.

Publish a useful finding when its evidence supports the exact wording. A plan, merged change, passing build, source card or matching hash is not a verified outcome. Progress may be shared as progress, with what remains unknown stated beside it. Repeated runs and routine commits do not each need a new announcement.

Planned or pre-registered
A question and method are recorded. There is no result yet.
Prototype or fixture
A mechanism was exercised in the named demonstration or authored examples. This does not establish performance on unseen work or customer systems.
Measured result
Name the method, date, sample, environment and result record. State failures, uncertainty and what the measurement cannot establish.
Repeated by Odin
A rerun on another Odin machine can check repeatability. It is not independent replication by an outside team.
Outside replication
Use this description only with an identified outside reproducer, the method and result they checked, and a public report supporting that scope.

A hash identifies bytes; it does not validate the experiment or establish that a claim is true. An answer’s source card records attribution, not correctness. A dated recording is not a live service. Private evidence must be labelled author-reported where a reader cannot inspect or reproduce it.

The same boundary applies to page titles, social previews, feeds and Twitter/X or LinkedIn progress posts: the short version must retain any limitation that changes the meaning. Correct an overstatement where it appeared, preserve the earlier record and link the correction. This standard was clarified on 1 November 2026.

1. The question comes first.

In short: before the runs that count, we write down the question and what would count as a yes, and publish it.

The details +

Before any counted run, an experiment's pre-registration is written down and published. It states the question, what is measured, how it is scored, the decision rule, what the experiment may spend and its known limits. Each one lives in its own folder, for example experiments/self-verify/preregistration.json (EXP 012) or experiments/jev-gate/preregistration.json (EXP 005).

Where the analysis is code, the code is frozen with the question: EXP 008 pins its analysis script experiments/latent-handoff/analyse.mjs by hash in a dated amendment (experiments/latent-handoff/amendment-02.json), and EXP 005 recomputes its published results from the committed runs with experiments/jev-gate/results.mjs.

Two studies on this site were published without a pre-registration: EXP 013 and EXP 014, the MongoDB studies. They are numbered so they can be cited, and the experiment list marks them “not pre-registered”: their method and data are published, but nothing about them was fixed before they ran.

2. Frozen by sha256.

In short: each written plan is locked by its fingerprint (a hash), so a later change shows up as a new, dated file.

The details +

Each pre-registration has a .sha256 beside it, such as experiments/self-verify/preregistration.sha256, written when the record is pushed. The push time is the freeze time. After that the record does not change.

A change after the freeze is a new, dated file that names its parent by hash: an amendment (experiments/jev-gate/amendment-01.json, experiments/self-verify/amendment-01/amendment.json) or an erratum (experiments/jev-gate/erratum-01.json). The site build refuses to publish a record whose bytes no longer match its hash: see scripts/jev-gate-prereg.mjs and scripts/ledger-publish.mjs. The published copy under site/data/ (served as data/ on this site) is the record, byte for byte.

3. A spend bound on every run.

In short: every study has a spending limit, and says what happens when it is reached.

The details +

Every pre-registration bounds its spend (a spend block; EXP 005, the first, calls it spendCap): the most the run may cost and what happens when that bound is reached. In EXP 012, for example, the run stops and the experiment is published as incomplete, with the finished count; nothing is extrapolated.

Experiments that pay for model calls keep a per-call spend ledger next to their results, for example experiments/jev-gate/spend-ledger.jsonl, experiments/nina-changes/spend-ledger.jsonl and experiments/blueprint-floor/spend-ledger.jsonl.

4. Rules that can prove us wrong.

In short: the pass mark is fixed before the run, and a result that misses it stays published.

The details +

The decision rule is part of the frozen record, so the result cannot choose its own bar. Results are published whatever they show, and a refuted claim stays refuted. So far that includes EXP 005 (the claim is refuted), EXP 007 (the premise is refuted), EXP 009 (its first prediction is refuted) and EXP 012 (the answer is no). Each status sentence on the experiment list comes from the experiment's own note, unedited (scripts/experiment-ledger.mjs).

Before a pre-registration is written we sometimes run a few calibration calls. When we do, the record says so, and states what we expect, so the result can contradict it.

5. Checked before it is published.

In short: changes to this site are checked automatically, and our policy asks for a separate review before they are merged.

The details, and a wording correction of 2 November 2026 +

Changes to this site arrive as pull requests. On each one, the verify job in .github/workflows/publish.yml reruns the three recorded experiments with the released engine, runs every test, builds the site and checks it (links, anchors, transcript digests and the public export boundary, scripts/check.mjs). The same job runs again on every push to main, before the site is deployed.

Our review policy requires a separate review of the final change on its exact head before merge (AGENTS.md). A different agent or model can provide that code review; this is not external scientific peer review or independent reproduction of an experiment. A particular change’s review receipt must establish what was actually checked.

2 November 2026 wording correction: earlier copy said every change had review by “a different agent and model”. The policy requires a separate exact-head review; the recorded receipt establishes the reviewer and scope for a particular change. That earlier sentence did not establish a different model for every review.

One gap is disclosed here. On 22 October 2026 a pull request was merged while its verify job was still running; that job then failed on a fence test whose base had moved, while the push run on main passed. Since 23 October the current version of our landing tool refuses to merge a pull request in this repository until verify has passed on its exact head. That is a check in our own tooling, not yet on GitHub's side: a rule there that requires the same check is waiting on the repository owner, and until it exists an older copy of the tool, or a person merging by hand, could still merge early.

6. Rerun it yourself.

In short: these steps rebuild this site and rerun its recorded checks on your own computer.

You need git, Node 22, JDK 21 (with JAVA_HOME set to that JDK) and pnpm 10.11.1. Clone the repository: a ZIP download will not build, because the build reads git metadata. These are the same steps as Run locally in the README, one command per line, so they also paste into Windows PowerShell 5.1:

git -c core.autocrlf=false clone https://github.com/odin-labs-ai/odin-rnd
cd odin-rnd
npm install --global pnpm@10.11.1
pnpm install --frozen-lockfile --ignore-scripts
pnpm experiment
node scripts/run-roi-demos.mjs
pnpm test
pnpm build
pnpm check
pnpm serve
The details +

pnpm experiment reruns the three recorded experiments, pnpm test runs every check on the recorded evidence, pnpm build builds the site from the records and pnpm check checks links, digests and the export boundary. The clone line keeps the committed line endings, which the sha256 pins check byte for byte; on Linux and macOS that setting is already off. corepack enable also installs the pinned pnpm, but on Windows it needs an elevated shell (Run as administrator), so the steps use npm install --global pnpm@10.11.1, as CI does. pnpm test also needs python3 and bash on a POSIX system: on Windows, run it inside WSL or skip it.

The commands are in package.json and AGENTS.md; docs/VALIDATION.md records how the site itself was validated. For a single experiment, its folder holds the inputs and the frozen analysis; its field note says which parts you can rerun and which depend on a private corpus.

7. What this does not prove.

In short: most studies are small and some use private data, so read each result’s limits before you quote a number.

The details, and a wording clarification of 2 November 2026 +

Most experiments here are small: one laptop, one model or a few dozen cases. Several use a private corpus, so you can check the hashes, the method and the counts but not rerun the cases. We wrote the experiments ourselves, about our own tools. A pre-registration stops us from moving the bar after the fact; it does not make a narrow question broad. Each field note states its own limits; read them before quoting a number.

Two pages hold the lab to this mechanically: provider economics and selected evidence and open questions. The build stops if a number on either is not read from an experiment record and linked to it (scripts/number-provenance.mjs).

2 November 2026 wording clarification: the earlier Evidence link “what we have measured, and not” implied a complete inventory. The linked page presents selected published claims and open questions; this build check validates numbers shown there, not completeness.
